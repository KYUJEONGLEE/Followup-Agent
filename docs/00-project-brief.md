# FollowUp Agent Project Brief

## 1. 개요 및 배경

### 추진 배경

기존 GateLM 프로젝트를 통해 LLM 호출을 중계하고 제어하는 Gateway 계층을 구현했지만,
실제 사용자의 업무를 처리하는 LLM Application 계층까지는 다루지 못했다.

실제 업무에서는 단순히 사용자의 질문에 답변하는 것뿐 아니라,
업무 데이터 조회, 내부 정책 확인, 여러 정보의 종합, 후속 업무 생성처럼
여러 시스템과 데이터를 순차적으로 활용해야 하는 경우가 많다.

이에 사용자의 자연어 요청을 기반으로 필요한 정보와 도구를 선택하고,
여러 단계의 업무를 하나의 흐름으로 처리할 수 있는 AI Agent를 설계하고 구현한다.


### 해결할 문제

고객 상담과 후속 관리를 담당하는 운영 담당자는 업무를 처리하기 위해
고객 정보, 상담 이력, 업무 상태, 내부 정책 등을 각각 확인해야 한다.

이후 여러 정보를 종합해 어떤 고객에게 후속 관리가 필요한지 판단하고,
필요한 경우 별도의 시스템에서 후속 업무를 직접 등록해야 한다.

이 과정에서 반복적인 조회와 확인 작업이 발생하며,
관리 대상이나 후속 업무가 누락될 가능성도 있다.

본 프로젝트에서는 이러한 업무에서 필요한 정보를 자동으로 조회하고,
관련 정책과 데이터를 근거로 후속 관리 후보와 권장 조치를 제시하며,
사용자의 요청에 따라 실제 후속 업무까지 실행할 수 있는 AI Agent를 구현한다.


## 2. 목표 및 성공 지표

### 핵심 목표

- 자연어로 입력된 업무 요청을 이해하고 필요한 정보를 조회할 수 있는 Agent를 구현한다.
- 하나의 요청을 처리하기 위해 여러 데이터와 기능이 필요한 경우 필요한 작업을 선택하고 순차적으로 수행할 수 있도록 한다.
- 내부 문서와 실제 업무 데이터를 함께 활용하여 사용자에게 판단 근거와 권장 조치를 제공한다.
- 사용자의 명시적인 요청에 따라 후속 업무를 실제 시스템에 생성할 수 있도록 한다.
- 단순 질의응답이 아닌 `요청 → 정보 조회 → 근거 검색 → 판단 보조 → 업무 실행`의 전체 흐름을 구현한다.


### 성공 지표

- 정의한 핵심 업무 시나리오를 End-to-End로 수행할 수 있다.
- 하나의 요청에서 여러 기능이 필요한 경우 적절한 작업을 선택하고 순차적으로 실행할 수 있다.
- 내부 정책이 필요한 요청에서 관련 문서를 검색하고 해당 근거를 응답에 활용할 수 있다.
- 고객 데이터와 검색된 정책을 함께 사용하여 후속 관리 후보와 이유를 제시할 수 있다.
- 데이터 변경 작업은 사용자의 명시적인 요청 또는 승인 이후 실행된다.
- 동일한 업무 실행 요청이 재시도되는 상황에서도 의도하지 않은 중복 작업이 발생하지 않도록 검증한다.
- 주요 정상/실패 시나리오에 대한 테스트 결과를 기록한다.


### 기술 검증 항목

다음 항목은 프로젝트 시작 시 특정 기술을 미리 확정하지 않고 최소 실험을 통해 판단한다.

- 자연어 요청에서 필요한 Tool을 선택하고 여러 Tool을 연속 실행하는 구조를 어떻게 구성할 것인가?
- 여러 단계의 실행 상태, 분기, 사용자 승인 과정을 어떤 방식으로 관리할 것인가?
- 내부 정책 문서를 Agent가 활용할 수 있도록 검색 흐름을 어떻게 구성할 것인가?
- Tool의 입력과 출력은 어떤 형태로 정의하고 검증할 것인가?
- 실제 데이터를 변경하는 Tool의 재시도 및 중복 실행을 어떻게 제어할 것인가?
- LLM, Tool, 검색 과정에서 실패가 발생했을 때 어떤 범위까지 재시도하거나 사용자에게 반환할 것인가?


### 기술 검증 결과

- OpenAI Responses API 기반의 직접 Tool Execution Loop에서 단일·다단계 Tool Calling을 검증했다.
- LangGraph StateGraph에서도 실제 LLM의 Function Calling 결과에 따라 Tool 실행과 종료를 분기하는 흐름을 검증했다.
- `get_customer` 결과의 `customer_id`를 다음 `get_consultations` Tool 입력으로 사용하는 의존 관계가 있는 순차 실행을 검증했다.
- MVP의 Agent Workflow Orchestration Layer로 LangGraph를 채택한다. LLM 호출과 실제 Tool 실행은 기존 OpenAI JavaScript SDK 및 Backend 함수가 담당한다.
- 상세 비교 근거와 실행 trace는 `docs/technical-decisions/langgraph.md`에 기록한다.


## 3. 범위

### In-Scope

#### Agent Backend
- 자연어 업무 요청을 처리하는 Backend API
- LLM을 이용한 업무 요청 해석 및 Tool 선택
- 여러 Tool을 순차적으로 실행할 수 있는 Agent 실행 흐름
- LangGraph의 State, Node, Conditional Edge를 이용한 Agent 실행 흐름 및 상태 관리

#### 업무 데이터
- 고객 정보 관리
- 상담 이력 관리
- 후속 업무 관리
- 업무 수행에 필요한 관계형 데이터 모델 설계
- 데이터베이스 Migration 및 테스트 데이터 구성

#### Tool
- 고객 정보를 조회하는 Tool
- 상담 이력을 조회하는 Tool
- 필요한 업무 데이터를 조회하는 Tool
- 후속 업무를 생성하는 Write Tool
- Tool 입력값 검증 및 실행 결과 처리

#### 내부 문서 검색
- 후속 관리 기준 및 운영 정책과 같은 테스트 문서 구성
- 문서 검색을 위한 기본적인 RAG Pipeline
- 검색된 정책을 Agent의 판단 근거로 활용
- 검색 결과와 최종 응답의 연결 관계 확인

#### 실행 안정성
- Tool 실행 실패 처리
- LLM 호출 실패 및 Timeout 처리
- 잘못된 Tool 입력 처리
- 실제 데이터를 변경하는 Tool의 중복 실행 방지
- Agent 및 Tool 실행 과정 기록
- 요청 단위 실행 흐름 추적

#### 검증
- 대표 업무 시나리오 E2E 테스트
- Tool 선택 및 다단계 실행 테스트
- RAG 검색 테스트
- 중복 요청 및 실패 상황 테스트
- 주요 테스트 결과 기록

#### 기존 프로젝트 연동
- Agent의 LLM 요청을 GateLM을 통해 처리할 수 있도록 연동
- Agent → GateLM → LLM Provider 전체 흐름 검증


### MVP 구현 순서

LangGraph 기술 검증은 MVP 구현 전에 완료했다. 실제 MVP 구현은 아래 순서로 진행하며,
LangGraph를 NestJS Agent Backend에 연결하는 작업은 7단계에서 수행한다.

| 순서 | Task | 상태 |
|---:|---|---|
| 1 | NestJS Agent Backend 프로젝트 및 개발 환경 구성 | 완료 |
| 2 | 도메인 모델 및 PostgreSQL 스키마 설계 | 완료 |
| 3 | Migration / Seed 데이터 구성 | 완료 |
| 4 | Agent API 요청·응답 계약 정의 | 완료 |
| 5 | Tool 인터페이스 및 실행 구조 설계 | 완료 |
| 6 | 고객 정보 / 상담 이력 Read Tool 구현 | 완료 |
| 7 | LangGraph 기반 Agent Workflow 구현 | 완료 |
| 8 | 후속 업무 생성 Write Tool 구현 | 완료 |
| 9 | 사용자 승인 흐름 구현 | 완료 |
| 10 | 핵심 시나리오 E2E 검증 | 완료 |

10단계 완료는 Agent Backend MVP의 기본 Read/Write·승인 흐름이 완성됐다는 의미다.
Project Brief 전체 범위의 RAG, 실패 복구와 GateLM 연동은 이후 단계로 유지한다.

### 7단계 Agent Workflow 구현 범위

1~6단계에서 Backend, 데이터, API 계약, Read Tool을 준비한 뒤,
Agent의 핵심 실행 흐름을 LangGraph로 연결한다.

```text
사용자 요청
→ LangGraph LLM Node
→ Function Call 유무 판단
→ Tool Node
→ LLM Node
→ 최종 응답
```

- `get_customer(name)`와 `get_consultations(customer_id)`를 실제 Agent Tool로 구현한다.
- LLM이 Tool 호출 순서를 결정하고, Tool 결과를 다음 LLM 호출에 전달한다.
- Agent 실행 ID와 Node·Tool trace를 기록해 요청 단위 흐름을 확인한다.
- 테스트 데이터로 고객 및 상담 이력을 제공한다.
- RAG, Write Tool, 사용자 승인, 재시도, 외부 시스템 연동은 이후 단계로 미룬다.


### Out-of-Scope

- 사용자의 승인 없이 중요한 Write 작업을 완전히 자율적으로 수행하는 기능
- 실제 의료기관 또는 고객의 개인정보 사용
- Multi-Agent 시스템
- 자체 LLM 또는 Embedding 모델 학습
- 장기 기억 및 사용자 개인화
- 음성/이미지 등 멀티모달 기능
- 복잡한 조직 및 권한 관리
- 멀티테넌트 SaaS 기능
- 대규모 분산 인프라 및 Kubernetes
- 상용 서비스 수준의 프론트엔드 UI


## 4. 타깃 사용자 / 대상

### Primary User

고객 상담 및 후속 관리 업무를 담당하는 소규모 클리닉의 운영 담당자를 주요 사용자로 가정한다.

운영 담당자는 여러 고객의 상담 이력과 현재 상태를 확인하고,
내부 운영 기준에 따라 후속 관리가 필요한 고객을 찾아 필요한 업무를 처리한다.


### 사용자가 겪는 문제

- 고객별 정보와 상담 기록을 각각 찾아야 한다.
- 후속 관리 기준을 별도의 정책이나 가이드에서 확인해야 한다.
- 고객 상태와 정책을 직접 비교하여 필요한 조치를 판단해야 한다.
- 판단 이후 후속 업무를 별도로 등록해야 한다.
- 반복적인 확인 과정에서 관리 대상이 누락될 수 있다.


### 대표 업무 시나리오

운영 담당자가 Agent에게 다음과 같이 요청한다.

> 최근 상담 이후 후속 관리가 필요한 고객을 찾아서 필요한 조치와 이유를 알려줘.

Agent는 다음 과정을 수행한다.

1. 최근 상담 이력과 고객 정보를 조회한다.
2. 후속 관리와 관련된 내부 정책을 검색한다.
3. 고객 데이터와 정책을 종합하여 후속 관리가 필요한 후보를 찾는다.
4. 각 후보에 대해 판단에 사용한 정보와 정책 근거를 제시한다.
5. 필요한 후속 조치를 사용자에게 제안한다.
6. 사용자가 특정 고객에 대한 후속 업무 생성을 요청하면 해당 작업을 실행한다.
7. 실행된 작업과 결과를 사용자에게 반환한다.


### 추가 업무 시나리오

#### 상담 준비

> 김민수 고객의 이전 상담 내용을 확인하고 오늘 확인해야 할 내용을 정리해줘.

- 고객 정보 조회
- 이전 상담 이력 조회
- 관련 업무 가이드 검색
- 상담 전에 확인할 항목 정리


#### 후속 업무 실행

> 방금 확인한 고객 중 3명에게 후속 상담 업무를 등록해줘.

- 이전 Agent 실행 결과 확인
- 대상 고객 식별
- 사용자 요청 확인
- 후속 업무 생성
- 실행 결과 반환


## 5. 제약사항 및 일정

### 주요 일정

프로젝트 전체 기간은 약 2주로 제한한다.

- **프로젝트 정의 및 기술 검증:** 2026-08-19 ~ 2026-08-21
- **Agent MVP 구현:** 2026-08-22 ~ 2026-08-25
- **RAG 및 실행 안정성 개선:** 2026-08-26 ~ 2026-08-29
- **GateLM 연동 및 최종 검증:** 2026-08-30 ~ 2026-09-01


### 제약사항

- 개인 프로젝트로 진행한다.
- 2주 안에 핵심 업무 시나리오를 완성하는 것을 최우선으로 한다.
- Backend 중심으로 구현하며 복잡한 Web UI는 개발하지 않는다.
- 실제 고객 및 의료 데이터를 사용하지 않고 가상의 테스트 데이터를 사용한다.
- 외부 LLM API를 활용하며 자체 모델 학습은 진행하지 않는다.
- LangGraph는 기술 검증 결과를 바탕으로 MVP의 Agent Workflow Orchestration Layer로 채택한다.
- 추가 기능보다 핵심 업무 흐름과 정상/실패 상황 검증을 우선한다.
