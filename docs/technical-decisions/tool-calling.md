# OpenAI Tool Calling 기술 검증

## 검증 배경

Agent가 사용자의 자연어 요청에 따라 외부 기능을 선택하고 실행하기 위해
Tool Calling이 실제로 어떤 실행 구조를 가지는지 확인한다.

단순 API 사용법을 확인하는 것이 아니라,
향후 Agent Backend에서 LLM과 Tool 실행 계층의 책임을 어떻게 분리할지 결정하는 것을 목적으로 한다.

## 검증할 질문

1. LLM은 자연어 요청에서 적절한 Tool을 선택할 수 있는가?
2. Tool의 arguments는 어떤 형태로 반환되는가?
3. 여러 Tool이 필요한 경우 호출 흐름은 어떻게 구성되는가?
4. Tool이 필요하지 않은 요청은 어떻게 처리되는가?
5. Tool 입력이 잘못됐거나 실행에 실패하면 어떤 처리가 필요한가?
6. Tool 실행 책임은 Agent 구조에서 어느 계층이 가져야 하는가?

## 최소 실험

테스트 Tool

- get_customer
- get_consultations

테스트 케이스

- 단일 Tool 필요
- 여러 Tool 필요
- Tool 불필요
- 존재하지 않는 데이터 조회
- 잘못된 입력

## 4. 관찰 결과

### 기본 Tool Calling

- 자연어 요청에 따라 모델이 필요한 Tool과 arguments를 반환하는 것을 확인했다.
- Tool은 모델이 직접 실행하지 않으며, 실제 실행은 애플리케이션이 담당한다.
- Tool arguments는 JSON 문자열로 반환되어 애플리케이션에서 파싱이 필요하다.
- Tool 실행 결과는 `call_id`를 이용해 기존 Tool 호출과 연결하여 모델에 다시 전달한다.

### 다단계 Tool Calling

- 고객 이름만 제공된 요청에서 모델은 먼저 `get_customer`를 호출했다.
- `get_customer`가 반환한 `customer_id`를 이용해 모델이 `get_consultations`를 추가 호출했다.
- Tool 호출 순서를 Backend에 하드코딩하지 않아도 앞선 Tool의 결과를 바탕으로 다음 Tool을 선택할 수 있었다.
- 모델이 더 이상 `function_call`을 반환하지 않을 때까지 Tool 실행과 LLM 호출을 반복하면 다단계 요청을 처리할 수 있었다.

### Tool이 필요하지 않은 요청

- 일반적인 대화 요청에서는 `function_call` 없이 바로 최종 응답을 반환했다.
- 동일한 실행 Loop에서 Tool 사용 요청과 비사용 요청을 모두 처리할 수 있었다.

### 조회 결과가 없는 경우

- 존재하지 않는 고객을 조회하면 `get_customer`는 `null`을 반환하도록 구성했다.
- 모델은 존재하지 않는 고객 ID를 임의로 생성해 다음 Tool을 호출하지 않고, 고객을 찾을 수 없다는 응답을 반환했다.
- `not found`는 Tool 실행 실패와 구분되는 정상적인 도메인 결과임을 확인했다.


## 5. 발견한 문제

### Tool 실행 실패 시 전체 Agent 중단

`get_consultations`에서 의도적으로 예외를 발생시키자 예외가
Tool 실행 Loop 밖으로 전파되면서 Node.js 프로세스가 종료되었다.

현재 구조에서는 다단계 실행 중 하나의 Tool에서 예외가 발생하면
Agent가 실패 상황을 처리하거나 사용자에게 결과를 반환할 기회 없이 전체 실행이 중단된다.

따라서 Tool 실행 결과를 다음과 같이 구분하여 처리할 필요가 있다.

- 정상 실행 및 결과 반환
- 정상 실행이지만 조회 결과 없음
- 잘못된 Tool 입력
- Tool 내부 실행 실패

Tool 내부에서 발생한 예외가 실행 Loop 전체로 전파되지 않도록 하고,
실패 역시 Agent가 처리 가능한 결과 형태로 변환할 필요가 있다.
